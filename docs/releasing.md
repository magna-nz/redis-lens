# Releasing redis-lens

A release is cut by pushing a `vX.Y.Z` tag. The Release workflow (`.github/workflows/release.yml`,
generated by [dist](https://axodotdev.github.io/cargo-dist/) 0.32.0 from `dist-workspace.toml`) does the rest.

## Once: two repository secrets

Set these under Settings › Secrets and variables › Actions:

- `CARGO_REGISTRY_TOKEN`: a crates.io API token with the `publish-new` and `publish-update` scopes.
- `HOMEBREW_TAP_TOKEN`: a fine-grained GitHub token with Contents read and write on `magna-nz/homebrew-tap`.

## Each release

1. Bump `version` in `Cargo.toml`. Run `cargo update -p redis-lens` (or `cargo build`) so `Cargo.lock` follows.
2. In `CHANGELOG.md`, give the changes their version heading: `## [X.Y.Z]` or `## [X.Y.Z] - YYYY-MM-DD`.
   That section becomes the release notes and its heading the release title. A section headed only
   `## [Unreleased]` is not used.
3. Check it locally: `dist plan --tag=vX.Y.Z` lists what will be built and shows the notes it picked.
4. Merge to `main` through a pull request, as usual.
5. Tag the merged commit and push the tag:

   ```sh
   git switch main && git pull
   git tag vX.Y.Z && git push origin vX.Y.Z
   ```

## What the pipeline does, in order

1. **plan** runs `dist host --steps=create`. It fails if the tag does not match the version in `Cargo.toml`.
2. **custom-release-gate** (`release-gate.yml`) runs at the same time: fmt, clippy with `-D warnings`, the
   unit tests on Linux, macOS and Windows, and the integration tests against Redis 7.4, Redis 6.2 and Valkey
   in Docker.
3. **build-local-artifacts** waits for both, then builds a binary archive for each of the five targets.
4. **build-global-artifacts** builds the shell and PowerShell installers, the Homebrew formula, the source
   archive and the checksums.
5. **host** creates the GitHub Release with every artifact. It runs only if plan, the gate and both builds
   passed (the gate condition is a hand edit; see the `HAND-EDITED` comment in `release.yml`).
6. **publish-homebrew-formula** pushes `Formula/redis-lens.rb` to `magna-nz/homebrew-tap`, and
   **custom-publish-crates** (`publish-crates.yml`) runs `cargo publish`. Both run after the GitHub Release
   exists. Prereleases (such as `v0.2.0-rc.1`) skip both.
7. **announce** finishes the run.

On a pull request the same workflow only runs `dist plan`. The gate's jobs skip themselves there (CI
already runs the same checks) and nothing is built or published.

## If a step fails

- **Before host** (plan, the gate or a build): nothing was published. Fix it on `main`, delete the tag
  (`git push --delete origin vX.Y.Z` and `git tag -d vX.Y.Z`), tag the fixed commit and push again.
- **A build cancelled before it starts** with "The configuration '…' is not supported": GitHub retired the
  runner image dist picked for that target. Name a current one under `[dist.github-custom-runners]` in
  `dist-workspace.toml` (v0.1.0 needed `aarch64-apple-darwin = "macos-15"`), then re-tag as above.
- **The Homebrew or crates.io step** (after the GitHub Release exists): re-run the failed jobs from the
  Actions page. A crates.io version can never be changed or uploaded twice, so the publish job first asks
  crates.io whether this version is already there and skips the upload if it is. Re-running is safe. You can
  also run the "Publish crate" workflow by hand on the tag.
- A missing `HOMEBREW_TAP_TOKEN` fails the Homebrew job; a missing `CARGO_REGISTRY_TOKEN` fails
  `cargo publish`. The GitHub Release is already up in both cases. Add the secret and re-run the failed jobs.
- A version that went out broken cannot be replaced on crates.io. Yank it (`cargo yank --version X.Y.Z`)
  and release a new patch version.

## After changing `dist-workspace.toml`

`release.yml` has one hand edit (search for `HAND-EDITED`), and `allow-dirty = ["ci"]` stops dist from
overwriting it, so `dist generate` leaves the file alone. To regenerate: remove the `allow-dirty` line, run
`dist generate`, re-apply the edit as its comment says, and put the line back. `dist plan` must then pass.
